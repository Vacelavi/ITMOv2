# ADR: решение для первого рабочего сценария

- Статус: accepted
- Дата: 2026-09-15
- Ответственные: команда практики 1

## Контекст

Учебный сервис принимает diff PR и генерирует комментарий с помощью LLM. По TRAINING_PR.diff выявлены проблемы: отсутствие валидации входа (KeyError/500), отсутствие обработки ошибок LLM (500) и риск DoS/prompt injection из-за неограниченного и несанитизированного diff. Границы: сервис только советует (SCOPE-1), не approve/merge. Релевантные репоправила из кейса: SEC-1, API-1, REL-1, OUT-1, QA-1, OBS-1.

## Решение

Минимально достаточная архитектура для первого сценария:

1. Валидация входа на уровне API.
   - Pydantic-модель `ReviewRequest { diff: str }` с ограничением длины (API-1) и обязательностью поля.
   - Невалидный вход возвращает 422.
2. Санитайзинг diff перед LLM (SEC-1).
   - Redactor удаляет/заменяет потенциальные секреты на [REDACTED].
3. Контролируемый вызов LLM (REL-1).
   - Клиент LLM с timeout=10s, retry=0, обработкой исключений.
   - Ошибки маппятся в контролируемый ответ (4xx/5xx) без утечки содержимого prompt.
4. Ограничение размера и упрощение prompt.
   - Тримминг/усечение diff при превышении лимитов; отказ 413 при слишком большом теле (API-1).
5. Формат ответа (OUT-1).
   - Возвращаем структурированный JSON: `summary`, `risks` (≤3 элемента с file, line, evidence, risk), `checks`.
   - Для учебного сценария допускается "comment" как деградированный режим, но целевой контракт — OUT-1.
6. Наблюдаемость и приватность (OBS-1).
   - Логируются request_id, длительность и статус, без diff и ответа модели.

Это решение устраняет выявленные риски и сохраняет простоту реализации.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрали сейчас |
|---|---|
| Без Pydantic, ручные проверки | Повышает вероятность пропуска ошибок и снижает совместимость с OpenAPI |
| Асинхронный стриминг ответа LLM | Усложняет первый инкремент, не влияет на устранение базовых рисков |
| Вынесение LLM-вызова в очередь | Избыточно для первого сценария, увеличивает латентность и сложность |

## Последствия и главный риск

- Положительные последствия:
  - Предсказуемые коды ошибок (422/413/контролируемые 5xx).
  - Снижение риска утечки секретов и DoS.
  - Явный контракт API и лучшая совместимость с инструментами.
- Ограничения:
  - Ограничение длины diff может требовать пост-обрезки и потери части контекста.
  - Таймаут LLM ограничивает глубину анализа.
- Главный риск:
  - Недостаточная релевантность ответа при агрессивном усечении diff.
- Как проверим риск:
  - Наблюдать долю 5xx и время ответа; e2e: позитивный/негативный/граничный; интеграционные тесты на исключения LLM; нагрузочный кейс на большой diff.

```mermaid
    Client[Client/CI] --> API[FastAPI /api/reviews]
    API -->|Валидация (422)| Err422[Ошибка 422]
    API --> Redactor[SEC-1 Redactor]
    Redactor --> Prompt[Prompt Builder]
    Prompt --> LLM[LLM Client (timeout 10s)]
    LLM -->|OK| Parser[Parser/Formatter (OUT-1)]
    Parser --> Response[Response: summary/risks/checks]
    LLM -->|Ошибка| ErrMap[Error Mapper (REL-1)]
    ErrMap --> CErr[Контролируемая ошибка]
    API -.-> Logs[(OBS-1 Logs)]
```
